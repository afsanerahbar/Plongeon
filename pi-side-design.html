Pi-Side Capture Design

Components, class relationships, runtime call sequences, and build order for the Raspberry Pi half of the diving foot-placement tracker — the part that captures a frame, detects both feet, and packages/syncs an attempt record.

Components

Eleven classes in three kinds: an interface with two interchangeable implementations, plain data containers, and behavior classes wired together by one orchestrator.

interface FootDetector

detect(frame) → list[FootMeasurement]. The one seam that lets detection methods swap without touching the orchestrator.

implements FootDetector MarkerDetector

ArUco corner detection — primary method. Returns position + rotation per foot in one reading.

implements FootDetector PoseDetector

BlazePose heel/foot_index landmarks — markerless cross-check, position only.

value object FootMeasurement

foot_side, position_mm, angle_deg, confidence, source. No behavior.

geometry CalibrationManager

calibrate(points), pixel_to_world(x,y) → mm. Pure math, no I/O.

persistence CalibrationStore

save() / load() the homography to disk. Split out of CalibrationManager on review.

capture CameraCapture

start/stop the camera, get_frame(), crop_to_roi(frame).

event logic AttemptEventDetector

Watches the ROI for foot presence → absence; returns the last valid contact frame as the attempt trigger.

image output ThumbnailGenerator

generate(frame, measurements) → an overlayed image the coach can sanity-check. Extracted off AttemptRecord on review.

value object AttemptRecord

attempt_id, timestamp, diver_id, dive_type, left_foot, right_foot, thumbnail_path. to_dict() only.

local storage LocalBuffer

SQLite. save(record), get_unsynced(), mark_synced(id) — survives a Wi-Fi drop.

network CloudSyncClient

upload(record), upload_thumbnail(path), is_online() — talks to Supabase.

orchestrator CaptureService

run(). Composes everything above via constructor injection; the systemd entrypoint.

Class diagram

CaptureService depends on the FootDetector interface, never on MarkerDetector or PoseDetector directly — that one arrow is the whole point of the SOLID fixes from the earlier review.

Call sequences

Three flows: the steady-state per-frame loop, what happens once an attempt is detected, and the one-time calibration setup.

Build order

Bottom-up: verify each leaf in isolation before wiring it in, and leave CaptureService — pure integration — for last, since that's the easiest place to debug once everything it calls is already proven correct.

Milestone 1 — see a frame, see a marker
  1. CameraCaptureGet a live feed working first — confirms the camera, cable and libcamera install before anything else depends on it. Visually verifiable on its own.
  2. CalibrationStore + CalibrationManagerTestable offline against a static test image with known reference points — no live camera loop needed yet.
  3. FootDetector (interface) + MarkerDetectorTest on printed markers in a still photo first: detect corners, read off position and angle, before wiring into any loop.
  4. FootMeasurementTrivial data class — build it alongside MarkerDetector as its return type.
Milestone 2 — recognize an attempt
  1. AttemptEventDetectorTestable with a scripted sequence of fake FootMeasurement frames (presence → absence) before it ever sees a real camera.
  2. ThumbnailGeneratorTestable with one static frame and fake measurements — draw the overlay, confirm it looks right.
  3. AttemptRecordTrivial data class once left_foot/right_foot measurements exist to put in it.
Milestone 3 — persist and sync
  1. LocalBufferTestable independently — save and retrieve fake AttemptRecords against a throwaway SQLite file.
  2. CloudSyncClientVerify against the real Supabase project with dummy data before it's hooked into the live pipeline.
Milestone 4 — integrate
  1. CaptureServiceWire everything together last. By this point every dependency it injects has already been proven correct in isolation, so bugs here are almost certainly wiring, not logic.
  2. PoseDetectorAdd the second FootDetector implementation once the primary path works end to end — needed only as the markerless cross-check, not for a first working version.
