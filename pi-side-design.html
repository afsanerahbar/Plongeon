Pi-Side Capture Design

The Raspberry Pi half of the diving foot-placement tracker. Four foot markers (heel and toe on each foot) and a few board markers are detected in every frame; the board's position is recomputed each frame, and each foot marker is placed in 3D at its real height before the angle is computed. The independent study delivers Phases 0–1, offline first.

Phases

Risk-first: the hard questions (marker height, the moving board, camera clearance, markers on wet skin, ±1° at the pool) are answered in Phase 0, before anything else is built or bought.

0Feasibility · 2–3 weeksdeliverable

Coach questions answered. Pool site visit with a tape measure and the geometry worksheet. Pi, camera, foot and board markers on a temporary mount, battery-powered. Clips analyzed in a notebook; the 3D height fix and board-marker placement tested.

Exit: bench test passes in every case, including raised markers (max angle error under 1°); markers survive 10+ water entries; detected in ≥90% of planted frames; a camera position at ≤1.2mm per pixel that stays clear of the diver.

1Offline pipelinedeliverable

The Pi records a short grayscale clip per attempt during practice. Afterward the clips run through the pipeline: CSV, thumbnails, and a one-page session report.

Exit: the coach gets per-attempt numbers after each practice; repeated readings of the same planted foot agree within 0.5°.

2Cloud + simple dashboardstretch

Supabase tables; results upload after processing; a Streamlit dashboard shows history and consistency; the coach edits targets there.

Exit: the coach views trends from anywhere and sets targets.

3Real-time on the Pifuture work

Live pipeline, uploads during practice, permanent mount with PoE, systemd service, Start/End session.

Exit: results within seconds of each dive; runs a practice unattended.

4Mobile appfuture work

React Native: live view, session control, target editor, history.

Exit: the full product.

5Markerlessfuture work

BlazePose, classical CV, or a custom model trained on clips collected in earlier phases.

Exit: accuracy close to the markers, without markers.

Components

Phase 1 needs 21 classes: one interface, twelve behavior classes, and eight small dataclasses. An interface is added only once a second implementation exists, so detection and sessions start as plain classes.

Orchestrator and interface

orchestrator · P1CaptureService

Runs the pipeline over a FrameSource and stores each attempt locally. No network code.

interface · P1FrameSource

start(), read() → Frame or None at clip end, stop(). Two real implementations from Phase 1.

Frames and recording

FrameSource · P0, P1CameraCapture

The only class that talks to the camera (Picamera2, 1440×1080, short exposure, grayscale).

FrameSource · P1VideoFileSource

Plays a recorded clip back as frames with their original timestamps.

recording · P1ClipRecorder

Keeps the last seconds in memory; saves each attempt as high-quality grayscale JPEG frames.

Measurement

detection · P1MarkerDetector

Finds the four foot markers and the board markers (DICT_4X4_50). Returns MarkerDetections.

geometry · P1CalibrationManager

board_pose() every frame (solvePnP); to_world() places each marker at its real height and computes the angle in board coordinates.

persistence · P1CalibrationStore

save() / load() the lens calibration and board-marker layout.

event logic · P1AttemptEventDetector

One attempt per dive, even with a hurdle; measures at the moment the coach chose.

image output · P1ThumbnailGenerator

Draws heel/toe points, foot lines, and angles on the measured frame.

Session and storage

session · P1FixedSession

The session folder's details: diver, dive type, marker heights.

local storage · P1LocalBuffer

SQLite: save(), get_session(), get_unsynced(), mark_synced().

reporting · P1ReportWriter

CSV + one-page summary per session, readable without an app.

dataFrame

image, captured_at.

data · pixelsMarkerDetections

feet (list of FootKeypoints), board_markers (ID → corners).

data · pixelsFootKeypoints

foot_side, heel_px, toe_px, confidence.

dataBoardPose

data · board mmFootMeasurement

Phase 2 (stretch)

network · P2CloudSyncClient

The only class that talks to Supabase.

sync · P2SyncWorker

Uploads pending attempts on its own thread.

Interfaces added later, when a second implementation arrives: SessionProvider in Phase 3 (FixedSession and CloudSyncClient), FootDetector in Phase 5 (MarkerDetector and PoseDetector).

Entry scripts

script · P0–1calibrate.py

Lens calibration from checkerboard photos; records where each board marker sits on the board.

script · P1record.py

Creates a session folder (diver, dive type) and runs ClipRecorder during practice.

script · P1process_clips.py

After practice: every clip through CaptureService, then ReportWriter; Phase 2 also uploads.

script · futuremain.py

Phase 3 live mode on the camera, run by systemd.

Class diagram

Phase 1 classes, plus the Phase 2 stretch classes in dashed outline. FrameSource is the only interface: CaptureService runs unchanged on a recorded clip or the live camera.

Call sequences

The per-frame pipeline is the same for a recorded clip and the live camera. What changes between phases is the frame source and which script runs it.

Phase 1 build order

Phase 0 is notebook work; the parts that pass become these classes. Each step is tested on clips recorded in Phase 0, so most of Phase 1 happens at a desk.

  1. 1Frame + FrameSource + CameraCapture + VideoFileSourceRead a Phase 0 clip and the live camera through the same interface.
  2. 2CalibrationManager (lens) + CalibrationStore + calibrate.pyPort the notebook's lens calibration and board layout; results should match the notebook.
  3. 3MarkerDetector + MarkerDetections + FootKeypointsOn Phase 0 clips, the foot and board marker centers should match the notebook's.
  4. 4BoardPose + board_pose()Check the board's computed position against its known movement in a pool clip: it should follow the board down and back up.
  5. 5FootMeasurement + to_world() in 3D — re-run the bench testThe classes must reproduce the Phase 0 bench result in every case, including raised markers: maximum angle error under 1°. Don't continue until they do.
  6. 6AttemptTrigger + AttemptEventDetectorOn Phase 0 pool clips: exactly one trigger per dive, with the hurdle not counted as its own attempt.
  7. 7ThumbnailGeneratorThe overlay lines up with the feet on real frames.
  8. 8SessionContext + FixedSession + AttemptRecordSmall dataclasses and the session-folder reader, including marker heights.
  9. 9LocalBufferSave and read back records in a throwaway SQLite file.
  10. 10CaptureService + process_clips.pyThe full offline run over recorded clips, end to end.
  11. 11ClipRecorder + record.pyRecord a real practice: one grayscale JPEG clip per attempt; check the write speed and card space.
  12. 12ReportWriterThe first session report goes to the coach — Phase 1 is done.
  • Phase 2 (stretch) adds Supabase tables with row-level security, CloudSyncClient, SyncWorker, and the Streamlit dashboard.
  • Future work: Phase 3 adds main.py, systemd, the permanent mount, PoE, and the SessionProvider interface; Phase 4 the React Native app; Phase 5 the FootDetector interface with a markerless detector.
