Pi-Side Capture Design

The Raspberry Pi half of the diving foot-placement tracker: find four markers (heel and toe on each foot), convert them to board millimeters and foot angles, and record each attempt. Built in phases, offline first: prove the measurement on recorded clips, then go live.

Phases

Risk-first: the hard questions (markers on wet skin, pool lighting, mount angle, ±1° at the pool) are answered in Phase 0. Each phase ends with something the coach can use and a test that decides whether to continue.

0Feasibility · 1–2 weeks

Pi, camera, and printed markers on a temporary mount, powered by a USB-C power bank. Record clips at the bench and in one pool session; analyze them in a notebook on a laptop.

Exit: bench angle error under 1°; markers survive 10+ water entries; detected in pool light; the mount shows the whole takeoff zone at a steep angle.

1Offline pipeline

The Pi records a short clip per attempt during practice. Afterward the clips run through the pipeline: CSV, thumbnails, and a one-page session report.

Exit: the coach gets per-attempt numbers after each practice; repeated readings of the same planted foot agree within 0.5°.

2Cloud + simple dashboard

Supabase tables; results upload after processing; a Streamlit dashboard shows history and consistency, and the coach edits targets there.

Exit: the coach views trends from anywhere and sets targets.

3Real-time on the Pi

The same pipeline on the live camera, uploads during practice, permanent handrail mount with PoE power, systemd service, Start/End session in the dashboard.

Exit: results appear within seconds of each dive; runs a whole practice unattended.

4Mobile app

React Native: live view, session control, target editor, history.

Exit: the full product.

5Optional: markerless

BlazePose cross-check, classical-CV orientation, or a custom model trained on clips collected in Phases 0–3.

Exit: accuracy close to the markers, without markers.

Components

Twenty-four classes and four entry scripts. Three interfaces let the same pipeline run on recorded clips (Phase 1) and the live camera (Phase 3) without changes.

Orchestrator and interfaces

orchestrator · P1CaptureService

Runs the pipeline over any FrameSource and stores each attempt locally. No network code.

interface · P1FrameSource

start(), read() → Frame or nothing at clip end, stop().

interface · P1FootDetector

detect(frame) → list[FootKeypoints]; empty list when no foot is found.

interface · P1SessionProvider

current_session() → SessionContext or nothing; returns immediately, never waits on the network.

Implementations

FrameSource · P0, P1, P3CameraCapture

The only class that talks to the camera (Picamera2, 1440×1080, short exposure).

FrameSource · P1VideoFileSource

Plays a recorded clip back as frames with their original timestamps.

FootDetector · P1MarkerDetector

Primary. Four DICT_4X4_50 markers; each refined marker center becomes a heel or toe point.

FootDetector · P5PoseDetector

Optional cross-check: BlazePose heel and foot_index landmarks.

SessionProvider · P1FixedSession

The session read from a session folder, for processing that folder's clips.

SessionProvider · P2CloudSyncClient

The only class that talks to Supabase: uploads, plus a cached active session.

Behavior classes

geometry · P1CalibrationManager

Lens correction + homography. to_world() converts heel and toe to mm, then computes the angle.

persistence · P1CalibrationStore

save() / load() calibration data.

event logic · P1AttemptEventDetector

Takeoff zone in board mm. Both feet in, then gone → AttemptTrigger.

image output · P1ThumbnailGenerator

Draws heel/toe points, foot lines, and angles on the last-contact frame.

local storage · P1LocalBuffer

SQLite: save(), get_session(), get_unsynced(), mark_synced().

recording · P1ClipRecorder

Keeps the last seconds in memory; saves a high-quality clip around each attempt.

reporting · P1ReportWriter

CSV + one-page summary per session, readable without the app.

sync · P2SyncWorker

Uploads pending attempts and refreshes the session cache on its own thread.

Data objects

dataFrame

image, captured_at.

data · pixelsFootKeypoints

foot_side, heel_px, toe_px, confidence, source.

data · board mmFootMeasurement

foot_side, heel_mm, toe_mm, angle_deg, confidence, source.

dataAttemptTrigger

frame, keypoints {left, right}, measurements {left, right}.

dataSessionContext

session_id, diver_id, dive_type.

dataAttemptRecord

attempt_id, captured_at, session/diver/dive (null = unassigned), left_foot, right_foot, thumbnail_path.

Entry scripts

script · P0–1calibrate.py

Lens calibration from checkerboard photos, board calibration from reference markers.

script · P1record.py

Creates a session folder (diver, dive type) and runs ClipRecorder during practice.

script · P1process_clips.py

After practice: every clip through CaptureService, then ReportWriter; Phase 2 also uploads.

script · P3main.py

Live: CaptureService on CameraCapture with CloudSyncClient, plus SyncWorker. Run by systemd.

Class diagram

CaptureService only sees interfaces for frames, detection, and sessions. Swapping VideoFileSource for CameraCapture and FixedSession for CloudSyncClient is all Phase 3 changes in the pipeline.

Call sequences

The per-frame pipeline and attempt handling are identical in every phase. What changes is which implementation is plugged in and which script runs them.

Phase 1 build order

Phase 0 is notebook work; the parts that pass become these classes. Each step is tested on the clips recorded in Phase 0, so most of Phase 1 happens at a desk.

  1. 1Frame + FrameSource + CameraCapture + VideoFileSourceRead a Phase 0 clip and the live camera through the same interface.
  2. 2CalibrationManager + CalibrationStore + calibrate.pyPort the notebook's lens and board calibration; results should match the notebook.
  3. 3FootKeypoints + FootDetector + MarkerDetectorRun on Phase 0 clips; marker centers should match the notebook's.
  4. 4FootMeasurement + to_world() — re-run the bench testThe classes must reproduce the Phase 0 bench result: angle error under 1°. Don't continue until they do.
  5. 5AttemptTrigger + AttemptEventDetectorOn the Phase 0 pool clips: exactly one trigger per dive.
  6. 6ThumbnailGeneratorThe overlay lines up with the feet on real frames.
  7. 7SessionContext + SessionProvider + FixedSession + AttemptRecordSmall data classes and the session-folder reader.
  8. 8LocalBufferSave and read back records in a throwaway SQLite file.
  9. 9CaptureService + process_clips.pyThe full offline run over recorded clips, end to end.
  10. 10ClipRecorder + record.pyRecord a real practice: one high-quality clip per attempt.
  11. 11ReportWriterThe first session report goes to the coach — Phase 1 is done.
  • Phase 2 adds Supabase tables with row-level security, CloudSyncClient, SyncWorker, and the Streamlit dashboard.
  • Phase 3 adds main.py, the systemd service, the permanent mount, and PoE — no new pipeline classes.
  • Phase 4 adds the React Native app. Phase 5 adds PoseDetector or another markerless detector.
